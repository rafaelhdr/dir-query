## Context

The backend currently accepts PDF uploads (`POST /uploads`, see the `document-upload` capability) and writes them to `UPLOAD_DIR` — nothing reads them afterward. The frontend has a placeholder `/ask` page that intentionally does nothing. This change adds a retrieval-augmented pipeline: index uploaded PDFs with [llama-index](https://www.llamaindex.ai/), persist that index to disk, and answer questions against it using MiniMax as both the embedding and completion provider.

Research findings that shape this design (see proposal for context):
- `llama-index-llms-minimax` is an official, installable llama-index LLM integration for MiniMax's OpenAI-compatible chat endpoint. Verified directly by inspecting the installed package: `MiniMax(model=..., api_key=...)` wraps `OpenAILike`, falls back to the `MINIMAX_API_KEY` env var if `api_key` isn't passed, and takes **no `group_id` parameter at all** — the chat endpoint doesn't need one.
- There is **no** official `llama-index-embeddings-minimax` package, and MiniMax's current public API reference (`platform.minimax.io/docs`) does not document an embeddings endpoint at all as of this research — the `/v1/embeddings` shape found during the proposal step may be outdated, region-locked, or discontinued. A prior working example from the user (a local RAG script) also uses `HuggingFaceEmbedding` rather than MiniMax for embeddings, corroborating that MiniMax-hosted embeddings aren't a reliable option right now.
- **Decision, confirmed with the user**: embeddings use a local model (`llama-index-embeddings-huggingface`'s `HuggingFaceEmbedding`, model `BAAI/bge-small-en-v1.5`, matching the user's working example) instead of a MiniMax-backed embedding wrapper. MiniMax remains the LLM for answer synthesis only. This removes the need for `MINIMAX_GROUP_ID` entirely (per the package inspection above) and removes the "unverified API shape" risk from the original plan, at the cost of a larger backend image (PyTorch + transformers) and a one-time model download on first use.

## Goals / Non-Goals

**Goals:**
- Uploading a PDF triggers indexing in the background; the upload HTTP response is not delayed by indexing.
- The index survives across uploads *and* across container restarts (bind-mounted to disk on the host), and on startup the system syncs the upload folder against the persisted index — indexing any file not already indexed, without re-embedding files that are.
- Indexing and startup sync progress is visible via console/log output (start, finish, per-file success/failure) — no status API or UI.
- A backend endpoint answers a question using the persisted index and the MiniMax LLM, and the `/ask` page is wired to it.
- Embeddings (indexing and query-time retrieval) use a local model, no external API or key required for that part. MiniMax (API key required) is used only for answer synthesis.

**Non-Goals:**
- No indexing status UI, progress endpoint, or websocket/polling mechanism — console logs only, per explicit instruction.
- No content-change detection — since uploads are write-only and immutable (each stored filename is unique, no update/replace endpoint exists), "already indexed" is a simple membership check by stored filename, not a hash/mtime comparison.
- No retry queue or dead-letter handling for failed indexing — a failure is logged and the file is simply left un-indexed (it will be picked up on the next startup sync, since it's still "not yet indexed").
- No CRUD, listing, or deletion of indexed content — consistent with `document-upload` being upload-only.
- No streaming answers, no chat history/multi-turn conversation, no citations UI beyond (optionally) listing source filenames.
- No authentication on the new `/ask` endpoint.
- No integration with a cloud secrets manager (e.g. AWS Secrets Manager, Vault) — Docker Compose file-based secrets for local dev only.

## Decisions

### 1. Background execution: FastAPI `BackgroundTasks`, no external task queue
Indexing a single uploaded file runs as a `BackgroundTasks` callback added by `POST /uploads` after the file is written. Because the callback is a plain (non-async) function, Starlette runs it in its threadpool, so it does not block the event loop or other requests.
- **Alternative considered**: a real task queue (Celery, RQ, arq). Rejected for this beta — a single-process backend with a threadpool-backed background task is sufficient for the current scale (no multi-worker deployment, no need for durability of pending jobs across restarts since startup sync will pick up anything not yet indexed anyway).

### 2. Startup sync: incremental, non-blocking, kicked off from the FastAPI lifespan
On startup, a lifespan handler schedules `sync_index()` (`asyncio.create_task(asyncio.to_thread(sync_index))`) rather than awaiting it — the server starts accepting requests (e.g. `/health`) immediately while syncing proceeds in a background thread. `sync_index()` loads the persisted index from `INDEX_DIR` if present (or starts a fresh empty one), diffs the set of stored filenames in `UPLOAD_DIR` against the set of filenames already represented in the index (see Decision 3 for how that set is tracked), and only loads/embeds/inserts the files not yet present — it does **not** re-embed files already indexed. Console logs report the diff up front (`"Startup sync: N upload(s) found, M already indexed, K to index"`) and then completion (`"Startup sync: complete"`), or `"Startup sync: nothing new to index"` when `K == 0`.
- **Alternative considered**: always fully rebuild from scratch on every startup (the original plan). Rejected after reconsidering the cost: combined with the bind-mounted `INDEX_DIR` (Decision 5), a full rebuild would re-pay the entire MiniMax embedding cost on every `docker compose down && up` for no reason, since the previous work is sitting right there on disk. Incremental sync keeps the same guarantee (everything in the upload folder eventually gets indexed, including files uploaded while the backend was down) at a fraction of the cost after the first run.
- **Alternative considered**: block startup until sync finishes. Rejected — with many/large new PDFs this could make container health checks and local dev iteration slow for no benefit; nothing requires the index to be fully caught up before the server accepts traffic (uploads still succeed; `/ask` against a not-yet-synced index just answers based on whatever's indexed so far, logged clearly).

### 3. Each document's `doc_id` is its stored filename; that's the single source of truth for "already indexed"
When a file is inserted into the index (whether from the upload path or the startup sync path), its llama-index `Document`(s) are given `doc_id`/`ref_doc_id` equal to the stored filename (the UUID-prefixed name from `document-upload`, which is unique and immutable — there's no update/replace endpoint). "Already indexed" is then just: is this filename a key in `index.ref_doc_info`? This avoids maintaining a second, hand-rolled manifest file that could drift out of sync with what the index actually contains — the index's own docstore is the only source of truth.
- **Alternative considered**: a separate `indexed_files.json` manifest listing filenames already processed. Rejected — two sources of truth (the manifest and the actual docstore contents) can drift if one write succeeds and the other doesn't (e.g. a crash between updating the manifest and persisting the index); keying directly off `ref_doc_info` makes that class of bug impossible.

### 4. A single in-process index + a lock serializes all mutations
The loaded `VectorStoreIndex` is held as a module-level singleton in `app/rag/index_service.py`. A `threading.Lock` wraps every mutation (insert-on-upload, sync-on-startup, and the persist-to-disk call that follows each), so an upload landing mid-startup-sync — or two uploads landing close together — cannot corrupt the persisted store. Callers waiting on the lock simply block in their threadpool thread until it's free.
- **Alternative considered**: no locking, relying on it being "unlikely" in practice. Rejected — file-backed persistence (`StorageContext.persist`) is not safe under concurrent writers, and this is cheap insurance.

### 5. Index storage: llama-index defaults, bind-mounted to the host like `UPLOAD_DIR`
Uses llama-index's default `SimpleVectorStore` / `SimpleDocumentStore` (no external vector DB), persisted via `StorageContext.persist(persist_dir=INDEX_DIR)` with `INDEX_DIR` defaulting to `/data/index` inside the backend container, bind-mounted from `./backend/data/index` on the host — the same pattern as `UPLOAD_DIR`/`backend/data/uploads`. `.gitignore` excludes its contents (with a `.gitkeep`), since it's fully regenerable from the upload folder.
- **Alternative considered (and originally chosen)**: keep the index container-local only (no bind mount), on the reasoning that startup always fully rebuilds anyway so durability wasn't load-bearing. Superseded by Decision 2: once startup sync became incremental, durability across `docker compose down`/`up` directly determines whether that restart is cheap (nothing new to embed) or expensive (re-embed everything) — so bind-mounting is now worth doing. If the bind-mounted directory is ever deleted or corrupted, startup sync just treats every upload as new and rebuilds from scratch, so this remains safe either way.

### 6. Embeddings: local `HuggingFaceEmbedding` (`llama-index-embeddings-huggingface`), model `BAAI/bge-small-en-v1.5`
No external API or credential is needed for embeddings. `Settings.embed_model` (or an explicit `embed_model=` passed to the index) is a `HuggingFaceEmbedding(model_name="BAAI/bge-small-en-v1.5")`, matching the user's own validated reference implementation. The model (~130MB) downloads from the Hugging Face Hub on first use and is cached by `sentence-transformers`/`transformers` under `HF_HOME`.
- **Alternative considered**: MiniMax-backed embeddings (the original plan). Rejected after verification showed no official package and no documented public endpoint for it (see Context) — building a wrapper against an unverified, possibly-defunct API risked shipping something that fails at runtime with no fallback.
- **Alternative considered**: `llama-index-embeddings-langchain` wrapping LangChain's `MiniMaxEmbeddings`. Moot once MiniMax embeddings were dropped, but was already a weaker option than either the (abandoned) direct wrapper or local embeddings — pulls in LangChain for one HTTP call.
- **Trade-off accepted**: this pulls PyTorch + `transformers` into the backend image. Pinned to CPU-only PyTorch wheels (`[tool.uv.sources]` → `download.pytorch.org/whl/cpu`) rather than the default PyPI `torch`, which otherwise drags in the full CUDA/cuDNN/NCCL stack (~5GB vs. ~1.2GB) for a container that has no GPU access configured. Note: `torch` must be listed as a **direct** dependency in `pyproject.toml` (even though nothing imports it directly) for uv's source override to actually apply — it's pulled in transitively via `sentence-transformers`, and uv does not apply `tool.uv.sources` overrides to transitive-only requirements. Verified empirically during implementation.

### 6a. The embedding model's Hugging Face cache is bind-mounted, like `INDEX_DIR`
Following the same reasoning as Decision 5, `HF_HOME` is set to a directory (default `/data/hf-cache`) bind-mounted from `./backend/data/hf-cache` on the host. Without this, every `docker compose down && up` (a fresh container) would re-download the ~130MB model from the Hugging Face Hub, adding startup latency and a network dependency that contradicts the whole point of Decision 2's incremental sync.

### 7. LLM: `llama-index-llms-minimax`
Used for answer synthesis in the query engine. Configured via `MINIMAX_API_KEY` and a `MINIMAX_LLM_MODEL` env var, defaulting to the package's own default (`MiniMax-M2.7`) but kept configurable since MiniMax's model lineup changes over time. No `group_id` is needed — confirmed by inspecting the installed package, which only accepts `model`/`api_key`/`api_base`/`temperature`.

### 8. PDF parsing: `llama-index-readers-file`'s PDF reader
Both the per-upload indexing path and the startup sync use the same "load documents from a directory of PDFs" helper (`SimpleDirectoryReader` scoped to `UPLOAD_DIR`, filtered to `.pdf`, using the bundled PDF reader, with `doc_id` set per Decision 3). The per-upload path loads just the one new file; the startup path loads only the files identified as not-yet-indexed.

### 9. `POST /ask`: synchronous JSON response, form-encoded question
The endpoint accepts a form field (`question: str = Form(...)`) rather than a JSON body, matching what an HTML `<form>` (or htmx, which posts as `application/x-www-form-urlencoded` by default) sends without extra JS. It builds a query engine from the current in-memory index using the MiniMax LLM and returns `{"answer": "...", "sources": ["<filename>", ...]}` synchronously (no streaming). If the index has no documents yet, it returns a clear message instead of an error (e.g. `{"answer": "No documents have been indexed yet.", "sources": []}`).

### 10. `/ask` page wiring
The form gets `hx-post="/api/ask" hx-swap="none"` — htmx's default swap is disabled because the response is JSON, not HTML, and the answer text is LLM-generated (i.e., untrusted): dumping it via `innerHTML` would be an XSS risk if the model ever echoed HTML/script content back (e.g. from a crafted PDF). Instead, a single `htmx:afterRequest` listener on the form parses `evt.detail.xhr.response` as JSON and renders it (success or error) into `#answer` using `textContent`/DOM `createElement`, never `innerHTML`, for both the answer and the source-filenames list.

### 11. Failures are logged, never crash the process
Indexing (per-file or startup sync) and `/ask` wrap MiniMax calls and PDF parsing in `try`/`except`, logging the error and — for indexing — simply leaving that file un-indexed (it stays eligible for the next startup sync); for `/ask`, returning a `502`-style error response with a clear message. A missing/invalid `MINIMAX_API_KEY` must not prevent the backend from starting or serving `/health`/`/uploads`.

### 12. MiniMax credentials: a read-only bind mount of `secrets/` at `/run/secrets`, with a plain env var fallback
`backend/app/config.py` reads `MINIMAX_API_KEY_FILE` (defaulting to `/run/secrets/minimax_api_key.txt` — note the `.txt`: since the mount is a plain directory bind (not Compose's native `secrets:` construct), the filename is preserved as-is rather than renamed to the bare secret name) and, if that file exists and is non-empty, reads the key from it; otherwise it falls back to the plain `MINIMAX_API_KEY` environment variable (also treated as absent if empty). `docker-compose.yml` mounts the whole `./secrets` directory read-only into the backend service at `/run/secrets`, so `secrets/minimax_api_key.txt` shows up at `/run/secrets/minimax_api_key.txt` — the exact path `_read_secret` looks for. The actual secret file is never committed: `.gitignore` excludes `secrets/*` except a `.gitkeep` and a `secrets/minimax_api_key.txt.example` placeholder that documents the expected format.
- **Bug found and fixed during implementation**: the default path was initially written as `/run/secrets/minimax_api_key` (no extension), a leftover assumption from the original Compose-native-`secrets:` plan (where Compose always mounts at `/run/secrets/<secret-name>` regardless of the source file's actual name). Once switched to a plain bind mount (see below), the real mounted path kept the `.txt` extension, so the secrets-file path silently fell through to "not configured" until caught by live end-to-end testing against the real MiniMax API.
- **Superseded approach**: originally planned as Docker Compose's native top-level `secrets:` block (`secrets: [minimax_api_key]` on the service, with a matching top-level `secrets: minimax_api_key: file: ./secrets/minimax_api_key.txt`). **Verified empirically during implementation that this fails hard**: if the referenced file doesn't exist, `docker compose up` refuses to start *any* service in the file (not just `backend`) with `Error response from daemon: invalid mount config for type "bind": bind source path does not exist`. Since the whole point of Decision 12 is that the plain-env-var fallback should work standalone (no secrets file required), this directly broke the design — a fresh clone with no `secrets/minimax_api_key.txt` couldn't even start `docker compose up`, regardless of which credential mechanism was intended. A plain bind mount of the `secrets/` *directory* (present via a committed `.gitkeep`, so the directory itself always exists) sidesteps this: Docker only requires the mounted directory to exist, not its individual file contents, so the container starts fine whether or not the real secret file has been created yet.
- **Alternative considered**: plain environment variable only (`MINIMAX_API_KEY` set in `.env` / `docker-compose.yml` `environment:`). Rejected as the *sole* mechanism — plain env vars are visible via `docker inspect`, process-environment dumps, and are one accidental `git add .env` away from being committed. File-based secrets avoid all three, and cost nothing extra in code (one small "read from file if present" helper). Kept as a fallback — not removed — for contexts where mounting a secrets file isn't convenient (e.g. some CI runners, PaaS platforms that only support injecting env vars), so the same image works either way.
- **Alternative considered**: `docker compose --env-file`-only secrets via `.env`, treating that file itself as the "secret". Rejected — `.env` is a general-purpose config file already used for port overrides (see the foundation change) and is easy to `.gitignore` incompletely or paste into a support channel by accident; a dedicated `secrets/` directory makes the sensitive material visually and structurally distinct from ordinary config.

## Risks / Trade-offs

- **[Risk]** If the local embedding model is ever changed (e.g. a future upgrade to a better model), startup sync won't re-embed already-indexed files — they'd keep their old embeddings indefinitely, since "already indexed" only checks presence, not which model produced the embedding. → **Mitigation**: out of scope for this change; a future change can add a way to force a full rebuild (e.g. deleting `backend/data/index/` locally, or an admin/CLI trigger) if/when the embedding model changes.
- **[Risk]** `BAAI/bge-small-en-v1.5` is a small, general-purpose, English-only embedding model — retrieval quality on non-English or highly domain-specific PDFs may be mediocre. → **Mitigation**: accepted for this beta; the model is swappable in one place (`index_service.py`) if quality proves insufficient.
- **[Risk]** Concurrent uploads racing the startup sync could serialize on the lock and make some uploads' background indexing appear slow. → **Mitigation**: acceptable for beta traffic levels; indexing is still "eventually" correct, just queued behind the lock.
- **[Risk]** No visibility into indexing failures beyond console logs — a user who uploads a corrupt PDF gets a success response for the upload but the file is silently never indexed. → **Mitigation**: explicitly scoped as a non-goal (no status UI yet); logged clearly so it's discoverable via `docker compose logs backend`; also, since "already indexed" is checked at every startup, a failed file remains eligible and gets retried on the next restart.
- **[Risk]** A locally created `secrets/minimax_api_key.txt` file could be accidentally committed if `.gitignore` is misconfigured, bypassed with `git add -f`, or a contributor copies the key into `.env` instead. → **Mitigation**: `.gitignore` excludes `secrets/*` except the `.gitkeep`/`.example` placeholders (Decision 12); `AGENTS.md` documents the expected local setup so contributors don't reach for `.env` out of habit.
- **[Risk]** The backend image is now materially larger (PyTorch + `transformers`, ~1.2GB even pinned to CPU-only wheels) and the first `/uploads` or startup sync after a fresh container triggers a ~130MB model download from the Hugging Face Hub. → **Mitigation**: CPU-only PyTorch wheels keep this to ~1.2GB instead of ~5GB (Decision 6); the model cache is bind-mounted (Decision 6a) so the download only happens once per host, not on every container recreation.

## Migration Plan

No data migration. `backend/data/index/` and `backend/data/hf-cache/` (both bind-mounted, gitignored) are created empty on first run and populated by the first startup sync / first embedding call respectively — deleting either locally is always safe (index: next startup treats every upload as new; HF cache: next embedding call just re-downloads the model). Before running, a contributor must supply a MiniMax API key (needed only for `/ask`, not for indexing) via **either** mechanism: create `secrets/minimax_api_key.txt` (copied from the committed `secrets/minimax_api_key.txt.example`) — the recommended path — **or** set `MINIMAX_API_KEY` as a plain environment variable (e.g. in `.env`) if a secrets file isn't convenient. `MINIMAX_LLM_MODEL` and `INDEX_DIR` remain plain env vars (not secrets). Without a MiniMax API key configured, uploads and indexing still succeed (embeddings are local and need no key); only `/ask` returns a clear configuration error rather than crashing. Rollout is `docker compose up --build`; rollback is reverting the change (uploads keep working either way, since `document-upload` is unaffected).

## Open Questions

- Should indexed content (chunks/nodes) ever be inspectable for debugging, given there's no status UI? Deferred — `docker compose logs backend` plus direct inspection of `INDEX_DIR` inside the container is the escape hatch for now.
- Should the embedding model be configurable via env var (like `MINIMAX_LLM_MODEL` is for the LLM) rather than hardcoded to `BAAI/bge-small-en-v1.5`? Deferred — hardcoding is simpler and the model is easy to change in one place if needed; revisit if retrieval quality becomes a concrete problem.
